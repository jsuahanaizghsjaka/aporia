## Сейчас, до приглашения тестеров

1. В OpenAI API пополнить баланс. Последний живой тест 1 октября вернул `AI_QUOTA`; чтение списка моделей не проверяет генерацию. Начать с $20, затем измерить расход.
2. Зарегистрировать новый аккаунт Aporia1 на production. Пароль владелец вводит самостоятельно. Проверить доставку и открытие письма, logout/login, восстановление пароля. Ссылка должна вернуться на production в том же браузере.
3. После пополнения: один полный реальный цикл — знакомство, подтверждение/редактирование профиля, цель, диагностика, маршрут, урок, проект, сохранение после входа, weekly review по фактическим данным. Повторить изоляцию другим аккаунтом.
4. Подтвердить замену ранее раскрытых секретов, если их ещё не заменили; значения не помещать в отчёт. Проверить текущие env после замены.
5. Провести первый тест по `FIRST_TESTER.md`, исправить P0/P1, затем начать alpha.

## 40. Alpha на 3–5 людях

Набрать начинающих Python/backend: хотя бы одного совсем начинающего, одного после курсов, одного с маленьким проектом. Лучше первые тестеры 18+, чтобы не усложнять согласование исследования. Это выбранная стартовая группа, а не изменение всей аудитории MVP.

Длительность: 4–5 дней после успешной приёмки. Дать людям цель и ссылку, не обучать интерфейсу заранее. Наблюдать первый проход с согласия, потом попросить 3–4 самостоятельных занятия. Канал связи и время интервью согласует владелец; автоматических рассылок нет.

Собирать: блокирующие ошибки, непонятные шаги, ожидание AI до первого текста и до конца ответа, бесполезные/неверные объяснения, потерю черновиков. В протоколе отдельно писать измеренное время и субъективное «долго».

После нескольких дней задать без подсказывания:

- Почему ты использовал бы Aporia вместо ChatGPT? В какой задаче всё же выбрал бы ChatGPT?
- В какой конкретный момент это помогло больше всего?
- Где хотел закрыть страницу? Что ожидал увидеть?
- Было ли понятно, что делать на следующем занятии?
- Чувствовал ли, что ментор учитывает твой уровень? Какой пример это подтверждает?
- Если продукт завтра исчезнет, чего именно будет не хватать?

Выход: таблица наблюдений, 3–5 ответов, найденный момент ценности, исправленные P0/P1 с повторной проверкой. Фраза «всем понравилось» без наблюдений не является результатом.

## 41. Feature Freeze

С 1 октября scope фиксируется на текущем Python backend. До v0.1 разрешены: исправления потери данных/доступа, непонятного текущего сценария, промптов/схем, подтверждённых проблем скорости и стоимости. Новые треки, голос, мобильное приложение и социальные функции идут в post-MVP backlog.

Каждая правка: наблюдение → минимальное изменение → проверка нужного сценария → запись результата. Приоритеты P0–P3 — в `FIRST_TESTER.md`. Для скорости сначала измерить минимум 10 однотипных вызовов: медиана/p95, объём контекста/ответа, доля ошибок, токены. Оптимизировать самый частый медленный участок; после изменения сравнить качество на тех же задачах. Не уменьшать лимит ответа вслепую: structured output может обрываться.

Замена модели не делается ради названия или низкой цены. Сравнить на одинаковых задачах: корректность JSON, следование Teaching Policy, сохранение памяти, качество подсказок, стоимость и задержка. При текущем `AI_QUOTA` базовые измерения ещё отсутствуют.

## 42. Beta на 10–20 людях

Запуск после исправлений alpha. По 5 новых человек в день удобнее для поддержки, чем 20 одновременно. Для каждого время отсчитывается от его регистрации:

| Период | Наблюдаем |
| --- | --- |
| D0, первые 24 часа | Знакомство, диагностика, начало и завершение первого урока |
| D1–D3 | Второй старт занятия, а не повторная отправка того же действия |
| D3–D7 | Начало проекта или сдача его задачи |
| D7, часы 168–192 | Учебное действие и открытие weekly review |

Запуск отчёта: `supabase/checks/stages40-43-cohort.sql` в SQL Editor. В приватной копии заполнить `cohort_ids` UUID только согласившихся новых тестеров; записать `as_of` для воспроизводимости. Не коммитить IDs/email. Аккаунты разработчика, демо, старые пользователи и автоматические fixtures исключить.

SQL только читает и выводит агрегаты. Пустая группа → `NO_COHORT`; период ещё не закончился → `WAITING_FOR_WINDOW`, процент NULL; нет signup event → `INCOMPLETE_HISTORY`. Последний случай требует проверки состава группы, а не ручного создания событий задним числом.

Ориентиры исходного плана: onboarding >70%, первый урок >60%, 3+ занятия >40%, D7 >25%, проект >30%, предпочтение Aporia для учебной задачи ≥50%. SQL фиксирует более точные окна: onboarding/первый урок в D0, 3 завершённых урока и старт проекта в D0–D6. Предпочтение собирается интервью, не выводится из кликов. Эти уточнения нужны для сравнения групп; их нельзя незаметно менять между запусками.

Всегда показывать числитель/знаменатель, например 3/5. Маленькая группа даёт гипотезы, а не статистическое доказательство спроса. D7 здесь — осмысленное учебное событие, не просто посещение страницы. Старт проекта или сдача задачи не измеряют чтение/редактирование кода: текущая телеметрия их не содержит.
