# Этапы 28–30 · Memory System, Prompts, Structured Outputs

Источник: этапы 28.1–28.5, 29.1–29.8 и 30.1–30.7 документа `MVP_AI_Mentor_Plan_September_2026.docx`. Изменения внесены в существующую Aporia. Новые ключи и миграции не нужны; источниками остаются таблицы профиля, цели, учебного состояния и сообщений.

## 28. Управляемая память

`src/lib/ai/memory.ts` собирает один пакет с версией и четырьмя разделами:

- **profile**: актуальные подтверждённые поля, интересы, предпочтения, график. Подтверждённая цель приоритетнее старого пожелания. Пустые поля сохраняются пустыми.
- **learning**: восемь навыков с mastery/confidence и числом доказательств, результат диагностики, до восьми недавних ошибок, активная сессия и действующий фокус. Модель не назначает эти оценки.
- **project**: проект, восемь задач и их состояния, сохранённые этапы, до восьми подтверждённых решений (по 500 символов). История чата и исходники всех задач сюда не копируются; проектный запрос отдельно получает код только текущей задачи.
- **recent**: до пяти последних занятий с датами, количеством ответов и результатом. Это ограниченная выборка, а не обещание полной истории.

Сборщик ничего не сохраняет и не смешивает источники разных пользователей. API сначала читает данные текущего аккаунта. Для задач, не загружающих учебную историю, `available=false`, неизвестный diagnostic_completed=null, список навыков пустой: неизвестность не подменяется нулевой оценкой.

В диалог модели идёт до восьми последних сообщений и не более 12 000 символов, по 4 000 на сообщение. Приоритет — последнему вопросу. Полная история остаётся в хранилище. Извлечение профиля дополнительно получает валидированный черновик Lesson 0: ранние подтверждённые факты не теряются при сокращении диалога. Общая память передаётся как данные отдельно от системных инструкций.

## 29. Промпты по задачам

`src/prompts/tasks.ts` — реестр независимых шаблонов с версией `2026-09-28.v1` и общей политикой работы с данными. Запрос получает один выбранный шаблон, а не весь реестр.

| Этап | Задача | Где используется |
| --- | --- | --- |
| 29.1 | onboarding | Lesson 0 + существующий проверяемый протокол function calling |
| 29.2 | diagnostic | объяснение диагностики в чате до её завершения; активная диагностика по-прежнему не допускает подсказок |
| 29.3 | roadmap | предложение порядка восьми навыков |
| 29.4 | teacher | выбор подходящего объяснения и применения в уроке |
| 29.5 | exercise | учебный диалог Learn со ступенями помощи |
| 29.6 | projectLearn / projectHelp / projectReview | вопросы, прямой разбор и статический обзор текущей задачи |
| 29.7 | weeklyReview | предложенный доступный фокус на неделю |
| 29.8 | resources | выбор разрешённых ресурсов |

Извлечение профиля, уточнение цели и обычный Help тоже имеют отдельные шаблоны. В пользовательские ответы не добавляются внутренние версии или названия контрактов.

## 30. Контракты и запись

`src/lib/ai/contracts.ts` связывает шесть контрактов с рабочими потоками:

- UserProfile — только кандидат; требует подтверждения.
- DiagnosticResult — результат серверной проверки, а не оценка, придуманная моделью.
- Roadmap — каждый навык один раз, с проверкой зависимостей.
- LessonAction — разрешённый выбор объяснения и применения; произвольные команды и оценки запрещены.
- MasteryUpdate — восемь серверных показателей по evidence; максимум mastery 95.
- WeeklyReview — валидированный сохранённый снимок; AI выбирает только разрешённый фокус.

`output.ts` проверяет статус completed, единственный текстовый JSON-ответ, отсутствие refusal, допустимые типы и схему результата. Повреждённый JSON, неизвестные поля прикладной схемы, недопустимые enum и незавершённые ответы не доходят до записи. Статический проектный обзор теперь использует strict JSON Schema. Текст обычного чата проходит проверку завершённого потока и длины; его текст не интерпретируется как команда изменения состояния.

Перед `commit_learning_state` дополнительно проверяются сохранённое состояние и производные контракты. CAS, идемпотентность и явное подтверждение изменений сохраняются. Схема проверяет форму, а не истинность произвольного объяснения: качество настоящей модели требует отдельной оценки.

Основа интеграции: [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Помимо strict-схемы приложение обрабатывает refusal и incomplete и выполняет собственную runtime-проверку.

## Целевые проверки

Остановить dev-сервер перед HTTP-прогоном:

```powershell
npm run test:architecture
npx tsc --noEmit -p tsconfig.stages28-30.json
npm run test:architecture:http
npm run dev
```

Проверяются только изменения этапов 28–30 и их вызовы API. Старые этапные наборы, общий `verify`, общий браузерный прогон и production build в эту проверку не входят. HTTP использует локальные Auth/AI/PostgreSQL fixtures, не платную модель и не производственные данные. Установленный ранее лимит `AI_QUOTA` не перепроверялся платными запросами.
